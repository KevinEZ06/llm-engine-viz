Continuous Batching：两种部署对比

一步 = 调度一批请求，做一次 model forward。Continuous batching = 按迭代拼 batch，不强制整请求跑完才换下一批。

对比项 统一引擎
Prefill + Decode 同机 		PD 分离
Prefill / Decode 分池
一步里谁进 batch 可同时含 prefill（常 chunked）与 decode 请求 P 侧：多个（chunked）prefill
D 侧：多个 decode
同一步通常不再 P+D 混批
Continuous batching 落点 单引擎内：混相负载一起拼 batch 两边各自 continuous batching
为什么这样拼 Decode 单 token 算力吃不满；掺 prefill 提高 GPU 利用率 避免 P/D 互相抢算力与调度；两侧按自身瓶颈优化
KV Cache 放哪 一套分页 KV 池（PagedAttention），P/D 请求共用 两套池：P 池 + D 池，不是共享同一块内存
P 算完写入本地 → RDMA/NIXL 等拷到 D → 之后主要在 D 池增长
传完后 P 侧通常释放该请求页，好接下一个 prefill
一步里 KV 怎么动 按请求各自的 block table：
Prefill 写新页；Decode 读旧页并追加 1 token		 P：只写（或 chunk 写）prompt KV 到 P 池
传输：把相关 block「搬」到 D 池
D：读已传入的 KV，每步追加 1 token
内存 / 调度约束 共享池；空页不够则少接 prefill 或抢占 两池内存与并发独立扩缩；还要考虑 KV 传输延迟、bootstrap，以及 P 侧传完释放是否及时
一句话 「一步混着算，KV 分页共一池」 「P 拼 P、D 拼 D；两池，算完再搬」

备注：Chunked prefill 在两种场景都常见——统一时用来避免长 prefill 堵死 decode；PD 时主要在 P 侧控制单步工作量与 TTFT。PD 的 KV 是「算完再搬」，不是跨机共享显存。
